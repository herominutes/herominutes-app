# LLM & Multi-Agent Architecture

How HeroMinutes uses AI specialists to build personalized injury recovery and proactive wellness plans.

---

## Overview

HeroMinutes employs a **multi-agent orchestration system** to generate customized plans. Rather than relying on a single AI call, the system simulates a multidisciplinary medical or wellness team — each agent brings domain expertise, and a coordinator synthesizes their contributions into a unified plan.

The architecture is designed around three principles:

1. **Specialization** — Each agent has a defined medical or wellness role with specific credentials and focus areas.
2. **Guaranteed delivery** — A tiered model cascade and deterministic fallbacks ensure every user receives a plan, even if all AI providers are unavailable.
3. **Progressive depth** — Guest users receive a 1-phase preview; authenticated users receive a full 5-phase, 10-week plan.

---

## Tiered AI Model Strategy

The multi-phase generation pipeline routes AI calls through a **tiered cascade** (`tieredAICall`) that attempts multiple models before failing. Some fallback code paths use separate model lists (including Gemma variants and direct API fetches).

### Primary Cascade (`tieredAICall`)

| Priority | Provider | Model | Role |
|----------|----------|-------|------|
| 1 | Google Gemini | `gemini-2.0-flash` | Primary engine |
| 2 | Google Gemini | `gemini-2.5-flash` | High-quality fallback |
| 3 | Google Gemini | `gemini-2.5-flash-lite` | Lightweight fallback |
| 4 | Google Gemini | `gemini-1.5-flash` | Legacy fallback |
| 5 | Groq | `llama-3.3-70b-versatile` | First cross-provider fallback (fast inference) |
| 6 | Mistral | `mistral-large-latest` | Second cross-provider fallback |
| 7 | DeepSeek | `deepseek-chat` | Final API-based fallback |

Each model is attempted with up to 2 retries before moving to the next. If all models fail, the system falls back to **deterministic plan generation** — hardcoded clinical logic that produces a safe, condition-appropriate plan without any AI involvement.

### Routing

All AI calls flow through a Supabase Edge Function (`gemini-proxy`) which acts as a secure gateway. API keys never reach the client. The `tieredAICall` function manages:

- Model selection and cascading
- JSON response parsing and validation
- Retry logic
- Structured error reporting

## Injury Recovery Plan Generation

### The 7 Recovery Specialists

Recovery plans are generated by a team of 7 virtual medical specialists:

| Specialist | Credentials | Domain | Focus |
|------------|------------|--------|-------|
| Cardiologist | MD, FACC | Clinical | Cardiovascular health, exercise tolerance, heart rate monitoring |
| Neurologist | MD, PhD | Clinical | Nervous system, neuromuscular control, movement disorders |
| Orthopedic Surgeon | MD, FAAOS | Clinical | Structural integrity, surgical recovery, tissue healing |
| Kinesiologist | PhD, CSCS | Movement | Movement science, biomechanics, exercise prescription |
| Physical Therapist | DPT, OCS | Movement | Rehabilitation protocols, manual therapy, ROM restoration |
| Sports Coach | MS, USAW | Performance | Training progression, return-to-sport protocols |
| Care Coordinator | MSN, RN | Performance | Synthesizes all specialist input, resolves conflicts |

### Specialist Generation

In Phase 1, all 7 specialists are generated via a single aggregate AI prompt. The system prompt instructs the LLM to role-play as a multidisciplinary team and return structured JSON with all 7 specialist analyses in one response.

If any specialist is missing from the AI output, a **deterministic fallback** fills the gap — a pre-written, clinically accurate template dynamically customized to the user's body region, pain level, and surgery history.

A **3-core domain architecture** is also defined in the codebase (grouping specialists into Clinical, Movement, and Performance domains for parallel generation), and may be activated in future optimizations.

### The 4-Step Generation Pipeline

After intake data is collected, plan generation proceeds through 4 sequential steps. Progress is logged to a `plan_generation_phases` database table after each step for debugging and analytics.

#### Step 1: Specialist Analysis

All 7 specialists analyze the user's intake data. Each specialist produces:

- **Case Assessment** — Analysis from their medical perspective
- **Key Recommendations** — Specific guidance for the plan
- **Red Flags** — Safety warnings and contraindications
- **Summary Bullets** — Patient-facing key points

#### Step 2: Exercise Structure

Using the specialist insights from Step 1, the LLM designs a progressive plan. Authenticated users receive a **5-phase plan** spanning 10 weeks; guest users receive a **1-phase preview**:

| Plan Phase | Weeks | Focus |
|------------|-------|-------|
| Phase 1 | 1-2 | Pain Management & Protection — gentle mobility, protect healing tissue |
| Phase 2 | 3-4 | Controlled Mobility & Activation — restore ROM, begin muscle activation |
| Phase 3 | 5-6 | Strength Building — progressive resistance, functional movements |
| Phase 4 | 7-8 | Power & Endurance — dynamic exercises, sport-specific preparation |
| Phase 5 | 9-10 | Return to Elite — full recovery, competition-ready, sport-specific performance |

The LLM selects 5 exercises per plan phase from condition-specific exercise libraries (e.g., `neck_injury_specific_seed.sql`, `knee_injury_specific_seed.sql`). Exercises are matched against the user's available equipment, age, and pain level.

#### Step 3: Exercise Detail Enrichment

For every exercise identified in Step 2, a separate AI call generates high-fidelity details:

- **Execution Steps** — 4-6 specific, actionable steps
- **Form Cues** — Technique reminders
- **Breathing Guide** — Inhale/exhale timing
- **Modifications** — Easier, harder, and joint-friendly alternatives
- **Duration/Sets/Reps** — Phase-appropriate programming

Each exercise is enriched individually via its own AI call to ensure quality and detail.

#### Step 4: Final Assembly

The system assembles the specialist analyses, enriched exercise phases, and safety guidelines into a complete `GeneratedPlan` object. This is returned to the client and auto-saved to Supabase for future access.

### Intake-to-Exercise Mapping Rules

Strict rules are injected into every prompt to ensure medical safety:

- **Pain Level 3 (High):** Only isometric holds, breathing exercises, and passive stretches. No dynamic movements.
- **Pain Level 2 (Moderate):** Slow controlled movements only. Avoid end-range. Light resistance in Phase 3+.
- **Early Post-Op (0-4 weeks):** Phase 1 extended. No resistance. Isometrics only.
- **Mid Post-Op (4-8 weeks):** Light resistance in Phase 2-3. Protect surgical repair.
- **Age 65+:** Must include chair-supported options.
- **Forbidden Exercises:** Each body region has a list of prohibited exercises enforced across all phases.

## Proactive Wellness Plan Generation

### The 5 Wellness Specialists

Proactive plans (Stretch & Flow, Posture) use a different team of 5 wellness specialists:

| Specialist | Credentials | Focus |
|------------|------------|-------|
| Mobility Specialist | DPT, FMS | Functional movement, joint-safe mobility |
| Flexibility Coach | MS, RYT-500 | Stretching protocols, yoga-informed flexibility |
| Posture Expert | DC, CCSP | Postural alignment, corrective positioning |
| Recovery Specialist | MS, CSCS | Athletic recovery, regeneration techniques |
| Mind-Body Coach | PhD | Somatic movement, breathwork, tension reduction |

### Specialist Generation

Similar to recovery, proactive specialists are generated via a single aggregate AI prompt in Phase 1. A **2-core domain architecture** (Flexibility and Wellness domains) is defined in the codebase for potential parallel generation optimization.

### The 4-Step Generation Pipeline

Proactive plans follow the same 4-step structure as recovery, adapted for wellness:

| Step | Purpose |
|------|---------|
| Step 1: Specialist Analysis | Wellness specialists analyze the user's work style, tightness areas, and goals |
| Step 2: Routine Structure | Defines the 5-phase weekly schedule and routine focuses (e.g., Morning Activation vs. Night Decompression) |
| Step 3: Exercise Details | Generates exercises with instructions, cues, breathing guides, and modifications (one AI call per exercise) |
| Step 4: Assembly | Compiles specialists + exercises into the final plan JSON and auto-saves |

Authenticated users receive a full **5-phase plan**; guest users receive a **1-phase preview**.

### Proactive Prompt Constraints

- Every exercise must have **4-6 specific execution steps**
- Exercises must match the user's **available equipment** (e.g., only yoga mat exercises if that's all they selected)
- Routines are tailored to the user's **session length preference** and **time-of-day** (morning vs. evening)
- Specialists flag **red flags** and follow **conflict resolution rules** (safety specialists override performance specialists)

## Safety & Quality Assurance

### Intake Compliance

User intake data is validated and transformed into structured prompt context before any AI call. This includes:

- Derived medical rules (e.g., "Pain Level 3 = Isometrics Only")
- Equipment progression guidelines (e.g., "Dumbbells: Phase 1 bodyweight, Phase 2 light dumbbell work, Phase 3-5 progressive loading")
- Age-appropriate constraints
- Surgery timeline calculations (weeks since surgery)

These rules are injected into every specialist and exercise generation prompt to ensure consistency across all agents.

### Conflict Resolution

When multiple specialists disagree, clear hierarchy rules apply:

- **Safety overrides performance** — If the Physical Therapist says "no loaded squats" but the Sports Coach recommends them, the safety constraint wins.
- **The Care Coordinator synthesizes** — The coordinator agent reviews all specialist inputs and resolves conflicts into a unified plan.

### Deterministic Fallbacks

The system guarantees plan delivery through multiple fallback layers:

1. **Missing Specialist Fallback** — If the AI fails to generate all required specialists, pre-written templates fill the gaps, dynamically customized to the user's data.
2. **Exercise Library Fallback** — If AI generation fails, the system attempts to build a plan from the condition-specific exercise seed database.
3. **Full AI Failure Fallback** — If all AI providers (Gemini, Groq, Mistral, DeepSeek) fail, the system generates a complete plan using hardcoded clinical logic (`buildProactiveFallbackPlan` for wellness, deterministic recovery templates for injury).
4. **Client-Side Fallback** — The frontend includes a local plan generator (`generateLocalProactivePlan`) as a last resort if the edge function is entirely unreachable.
